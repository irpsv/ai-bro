# ai-bro

![ai-bro](./assets/banner.png)

Любое дело делать лучше вместе, особенно со своим бро... AI бро!

AI bro - это набор скиллов, которые делают вашу работу с агентами гораздо удобнее, проще и эффективнее.

Он **НЕ навязывает** вам своё видение правильных паттернов и методологий, а **адаптируется** под ваши реалии и **помогает** работать в них.

## Установка

Просто скажите своему агенту установить плагин и он все сделает сам:
```text
Установи плагин из https://github.com/irpsv/ai-bro
```

Если вам нужен отдельный набор скиллов, а не целый плагин, то можно во-первых попросить об этом агента, либо воспользоваться тулзой `skills`:
```bash
npx skills add irpsv/ai-bro -g -s bro-think-with-me
```

### Cursor

В разделе `Customize` выбирайте `Plugins`, затем нажимайте `Add` и `From Github Repository`.

### Claude Code

В сессии Claude Code:
```text
Установи скиллы из репозитория https://github.com/irpsv/ai-bro
```

### Codex / ChatGPT

В разделе `Плагины` нажимайте `Добавить` и `Добавить маркетплейс`.

## Скиллы

### `/bro-init-memory-bank`

Создаёт memory bank с нуля: структуру каталогов и первичное заполнение контекста. Если банк уже есть, не перезаписывает его — пополнение идёт через `/bro-remember-it`.

```text
/bro-init-memory-bank заведи memory bank для этого проекта
```

### `/bro-think-with-me`

Совместно проясняет задачу и не меняет код и артефакты. По запросу выбирается один внутренний workflow:

- `explore` — мысль сырая, вопрос не сформулирован или в запросе смешаны несколько тем.
- `challenge-thinking` — есть идея, подход или вывод; нужно проверить логику, допущения и слабые места.
- `debug` — поведение отличается от ожидаемого, а причина неизвестна.
- `solve-problem` — проблема и причина уже понятны, нужно выбрать, как её решить или обойти.
- `design-solution` — нужно что-то добавить, изменить или спроектировать и выбрать подход.

```text
/bro-think-with-me мне нужно понять как лучше организовать удобный процесс для работы пользователя по сценарию авторизации
```

```text
/bro-think-with-me после последнего деплоя периодически падает создание заказа, помоги найти причину
```

### `/bro-give-me-spec`

Фиксирует, что должно получиться, без шагов реализации.

Механика скилла:

1. Интервью, чтобы закрыть дыры в задаче.
2. Черновик спецификации: результат, рамки и критерии приёмки.
3. Ревью черновика на согласованность, однозначность и проверяемые критерии, при необходимости на безопасность.

```text
/bro-give-me-spec зафиксируй спецификацию результата для rate limiting публичного API без шагов реализации
```

### `/bro-give-me-plan`

Составляет план реализации без кода.

Механика скилла:

1. Интервью, чтобы закрыть дыры в задаче.
2. Черновик плана: что сделать и в каком порядке.
3. Ревью черновика на согласованность, однозначность и шаги. Если в задаче есть доступ, секреты или права — ещё и на безопасность. Если упирается в выбор подхода или порядка — спрашивает. Остальные замечания закрывает сам.

```text
/bro-give-me-plan нужно составить план для добавления rate limiting на публичный API
```

### `/bro-review-spec-plan`

Независимо проверяет уже написанную спецификацию или план и возвращает отчёт, не правя артефакт. Отдельный вызов нужен, когда артефакт уже есть вне цикла `/bro-give-me-spec` и `/bro-give-me-plan`.

Ревью делают субагенты, оркестратор сам артефакт не оценивает: общее ревью и, при необходимости, проверка безопасности.

```text
/bro-review-spec-plan проверь спецификацию в memory-bank/changes/add-rate-limit/spec.md
```

### `/bro-do-it`

Берёт задачу в реализацию и доводит её до результата.

Механика скилла:

1. Если в задаче уже есть шаги — идёт по ним. Если шагов нет — сам выбирает способ по текущему коду.
2. Пишет код, коммитит и прогоняет быстрые проверки.
3. Отдаёт изменения на ревью. Замечания чинит сам и проверяет, что они закрыты, прежде чем звать ревью снова.
4. Проверяет тесты и критерии приёмки. Пока что-то не сходится — следующая попытка, не больше десяти. Когда всё сошлось, помечает спецификацию сделанной и записывает, что изменилось в проекте.

```text
/bro-do-it выполни спецификацию из memory-bank/changes/add-rate-limit/spec.md
```

```text
/bro-do-it выполни план из memory-bank/changes/add-rate-limit/plan.md
```

```text
/bro-do-it поправь текст ошибки в форме входа и добавь тест на этот сценарий
```

### `/bro-finish-it`

После сделанной работы коммитит, пушит, дописывает знания и убирает временные артефакты, пропуская то, что уже закрыто. В конце кратко показывает итог и предлагает оформить PR и запись в таск-менеджере.

```text
/bro-finish-it закрой текущую задачу
```

### `/bro-review-code`

Проверяет изменения без исправлений кода.

Для ограниченного изменения в одной подсистеме, без высокорисковых границ, текущий агент проводит комплексное ревью сам, без субагентов.

Для широкого или высокорискового изменения проверки запускаются параллельно. Если в изменении есть доступ, секреты или граница доверия, комплексный режим не используется.

- `requirements` — соответствие задаче и рамкам;
- `correctness` — корректность и регрессии;
- `security` — безопасность, при профильном ревью запускается всегда;
- `performance` — производительность;
- `tests` — полнота и качество тестов.

Остальные профили запускаются, когда их предмет есть в изменениях. Для локального, но рискованного изменения берутся только относящиеся к риску проверки вместе с корректностью и безопасностью.

```text
/bro-review-code проверь текущую ветку относительно main
```

### `/bro-remember-it`

Дописывает устойчивые знания о проекте — контекст, фичи, типовые процедуры — в уже существующее хранилище, без дублей. Рабочие спецификации и планы не создаёт.

```text
/bro-remember-it добавь в базу знаний описание фичи rate limiting
```

## Субагенты

Разбор кода, реализацию, ревью и проверку результата скиллы отдают субагентам. Оркестратор ведёт диалог и собирает итог, а перед запуском выбирает минимальный достаточный тир по сложности, неоднозначности и риску. Модель берётся первая доступная внутри этого тира. Если ни одна недоступна — режим auto или текущая модель сессии. Тир повышается только по правилу скилла и не понижается, если скилл задал его явно.

- `junior` — узкая предсказуемая работа: механическая правка по точной инструкции, выжимка фактов, проверка по чеклисту.
- `middle` — обычная работа: изменение или разбор нескольких связанных частей, локальные технические решения.
- `senior` — сложная, неоднозначная или рискованная задача, а также продолжение после неуспеха на `middle`.
- `critical` — только отдельная проверка безопасности.

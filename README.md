# ai-bro

![ai-bro](./assets/banner.png)

Когда мы постигаем что-то новое, всегда проще и удобнее это делать не в одиночку, с кем-то вместе, со своим бро... AI bro!

Работает со всеми популярными harness и оболочками!

## Почему он, а не ...

AI bro - это набор скиллов, которые делают вашу работу с агентами гораздо удобнее, проще и эффективнее.

Он **НЕ навязывает** вам своё видение правильных паттернов и методологий, а **адаптируется** под ваши реалии и **помогает** работать в них. Если в проекте уже есть свой флоу — OpenSpec, Spec Kit или другой — скиллы **встраиваются** в его этапы, а не заводят второй процесс.

## Установка

Установить глобально только универсальный скилл `bro-think-with-me`:
```bash
npx skills add irpsv/ai-bro -g -s bro-think-with-me
```

Обновить глобально только `bro-think-with-me`:
```bash
npx skills update bro-think-with-me -g
```

Установить весь набор:

Простой и привычный для всех путь:
```bash
npx skills add irpsv/ai-bro -g
```

Либо можете попросить своего агента:
```
Установи скиллы из репозитория https://github.com/irpsv/ai-bro
```

## Механика работы

Каждую задачу можно разбить на вполне конкретные и понятные этапы:
1. **Знакомимся** - понимаем, как устроен набор; при необходимости заводим memory bank.
2. **Думаем** - проясняем мысль, проверяем идею, ищем причину проблемы или выбираем подход.
3. **Специфицируем** - фиксируем, что хотим получить и по каким наблюдаемым условиям результат готов, не задавая способ реализации.
4. **Планируем** - при необходимости собираем однозначный план реализации без кода.
5. **Делаем** - непосредственно разрабатываем по спецификации, плану или задаче из диалога.
6. **Помним** - фиксируем устойчивые знания о проекте.

И на каждом из этих этапов вам поможет ваш бро.

### Знакомимся

Когда вы только подключили набор или заходите в новый репозиторий, скажите `/bro-on-board`, и ваш бро коротко покажет карту скиллов на примерах и типовой флоу.

Скилл `bro-on-board` проводит **tour** — знакомство с командами и этапами работы. Если memory bank ещё нет, он объяснит зачем он нужен и предложит следующий шаг — `/bro-init-memory-bank`.

Этот скилл сам автоматически не подключается, поэтому его лучше вызывать явно с помощью slash команды `/bro-on-board`.

Пример вызова:
```text
/bro-on-board расскажи как пользоваться
```

### Инициализируем memory bank

Когда нужно создать memory bank с нуля — структура каталогов и первичное заполнение контекста проекта — скажи `/bro-init-memory-bank`.

Скилл `bro-init-memory-bank` работает только если банка ещё нет. Если `memory-bank/index.md` уже существует — скилл не перезаписывает банк и направляет к `/bro-remember-it` для пополнения.

Этот скилл сам автоматически не подключается, поэтому его лучше вызывать явно с помощью slash команды `/bro-init-memory-bank`.

Пример вызова:
```text
/bro-init-memory-bank заведи memory bank для этого проекта
```

### Думаем

Когда нужно что-то поштормить, выбрать решение или разобраться, почему что-то сломалось, просто скажи `/bro-think-with-me`, и ваш друган придёт на помощь.

Внутри скилла `bro-think-with-me` заложены правила ведения удобного и комфортного диалога, а также поддержка разных вариантов общения:
- **Прояснение** — мысль ещё сырая, вопрос не сформулирован или в запросе смешаны несколько тем.
- **Проверка идеи** — есть идея, подход или вывод; нужно проверить логику, допущения и слабые места.
- **Дебаг** — наблюдаемое поведение отличается от ожидаемого, а причина неизвестна; собираем факты, проверяем гипотезы и ищем корневую причину.
- **Поиск решения** — проблема и её причина уже понятны, но неясно, как её лучше решить или обойти.
- **Выбор подхода** — нужно что-то добавить, изменить или спроектировать; выбираем, как это сделать.

Дебаг и поиск решения разделены: сначала скилл устанавливает, почему возник сбой, и только после этого по запросу пользователя переходит к обсуждению исправления. Все режимы работают в READONLY.

Скилл может подключаться автоматически в зависимости от текущего диалога, НО для надёжности и на длинных сессиях вы можете явно вызывать его с помощью slash-команды `/bro-think-with-me`.

Пример вызова:
```text
/bro-think-with-me мне нужно понять как лучше организовать удобный процесс для работы пользователя по сценарию авторизации
```

Пример дебага:
```text
/bro-think-with-me после последнего деплоя периодически падает создание заказа, помоги найти причину
```

### Специфицируем

Когда нужно зафиксировать, **что** должно получиться, но оставить технический путь исполняющему агенту, вызови `/bro-give-me-spec`.

Скилл создаёт спецификацию — файлом по указанному тобой пути или через план harness — с задачей и контекстом, целевым результатом, рамками и критериями приемки (при необходимости — с разделом принятых решений). Шаги реализации в спецификацию не входят. Текущие файлы в контексте допустимы как описание текущего состояния; технический путь решения не задаётся. Критерии приемки — наблюдаемые утверждения о результате, без пометки, как именно их проверять. Порядок тестов и реализации спецификация не задаёт.

Если спецификация записана файлом, скилл напрямую вызывает `/bro-review-spec-plan`. При успешном ревью её можно передать напрямую в `/bro-do-it`.

Пример вызова:
```text
/bro-give-me-spec зафиксируй спецификацию результата для rate limiting публичного API без шагов реализации
```

### Планируем

Когда задача уже более-менее понятна и пора превращать её в чёткий план действий, просто скажи `/bro-give-me-plan`, и ваш бро поможет собрать чёткий и понятный план, благодаря которому будет ясно, что именно нужно реализовать.

Для файлового плана скилл напрямую вызывает `/bro-review-spec-plan`. Замечания к формулировкам, путям и правилам шагов закрывает сам; развилку подхода уточняет одним вопросом. К человеку итоговый файл приходит после успешного ревью; тогда его можно передать напрямую в `/bro-do-it`.

Внутри скилла `bro-give-me-plan` два формата плана под одну задачу:
- **План в чате** (`inline`) — если задача небольшая, результат понятен и отдельный артефакт не нужен.
- **Файловый план** (`file`) — если план должен пережить новый чат или нужны явные разделы «Рамки» / «Критерии приёмки», создаётся файл плана по указанному тобой пути.

Крупные инициативы лучше сначала фиксировать спецификацией (`/bro-give-me-spec`), а планы составлять на конкретные небольшие задачи.

Этот скилл сам автоматически не подключается, поэтому его лучше вызывать явно с помощью slash команды `/bro-give-me-plan`. Перед составлением плана он собирает недостающий контекст, предлагает подходящий формат и просит подтвердить выбор.

Пример вызова:
```text
/bro-give-me-plan нужно составить план для добавления rate limiting на публичный API
```

### Делаем

Когда уже пора переходить от разговоров и планов к реальной разработке, просто скажи `/bro-do-it`, и ваш бро возьмёт задачу в работу и доведёт её до результата через реализацию и ревью.

`bro-do-it` работает в двух режимах:
- **plan** — если в постановке есть шаги реализации, строго следует заданным способу и порядку.
- **autopilot** — если шагов нет (спецификация или задача из диалога), сам выбирает технический подход по существующему коду.

Скилл выполняет до десяти итераций разработки. После быстрых проверок он коммитит изменения итерации, напрямую вызывает `/bro-review-code`, а затем передаёт финальную проверку тестов и покрытия независимому verifier-субагенту. После вердикта verifier `PASS` напрямую вызывает `/bro-remember-it`. Ошибки и доказательные findings возвращаются developer в следующую итерацию. В режиме `plan` любое содержательное отклонение от заданного способа требует решения пользователя; в `autopilot` технические неоднозначности разрешаются автономно, если они не меняют результат, безопасность, данные или публичный контракт.

Этот скилл сам автоматически не подключается, поэтому его нужно вызывать явно с помощью slash-команды `/bro-do-it`.

Пример вызова со спецификацией:
```text
/bro-do-it выполни спецификацию из memory-bank/changes/add-rate-limit/spec.md
```

Пример вызова с планом:
```text
/bro-do-it выполни план из memory-bank/changes/add-rate-limit/plan.md
```

Пример вызова без артефакта:
```text
/bro-do-it поправь текст ошибки в форме входа и добавь тест на этот сценарий
```

### Ревьюим код

Когда нужно независимо проверить уже сделанные изменения без исправления кода, вызови `/bro-review-code`.

Скилл проверяет:
- соответствие задаче и критериям приемки;
- корректность и возможные регрессии;
- безопасность;
- производительность;
- полноту и адекватность тестов.

Для ограниченного изменения текущий агент проводит одно комплексное ревью без вложенных субагентов. Для крупного или высокорискового изменения скилл может параллельно запустить применимые профильные проверки, а затем объединяет и нормализует findings.

`bro-do-it` напрямую вызывает этот же скилл после быстрых проверок и коммита перед ревью. Финальный запуск тестов и проверку покрытия выполняет отдельный verifier-субагент.

Пример самостоятельного вызова:
```text
/bro-review-code проверь текущую ветку относительно main
```

### Запоминаем

Когда нужно пополнить постоянный слой знаний о проекте — контекст, фичи, типовые процедуры — скажи `/bro-remember-it`, и ваш бро аккуратно добавит знания в то хранилище, которое уже есть в проекте.

Скилл `bro-remember-it` классифицирует знание по ролям (контекст, фичи, playbooks), берёт пути из инструкций проекта и записывает без дублей. Если устойчивого знания нет — сообщает, что писать нечего. Если разделы в контексте не видны — спросит, куда класть. Канонический memory bank с нуля по-прежнему создаёт `/bro-init-memory-bank`.

Скилл **не** создаёт рабочие артефакты задачи (спецификации результата и планы): для спецификаций используй `/bro-give-me-spec`, для планов — `/bro-give-me-plan`.

Этот скилл сам автоматически не подключается, поэтому его лучше вызывать явно с помощью slash команды `/bro-remember-it`.

Пример вызова:
```text
/bro-remember-it добавь в базу знаний описание фичи rate limiting
```

## Работа с другими инструментами

AI bro не подменяет OpenSpec, Spec Kit и похожие каркасы. Он закрывает то, чего у них обычно нет как отдельной дисциплины: совместное думание, независимое ревью, цикл реализации с проверками и постоянные знания о проекте.

На каждом этапе нужен **один** хозяин. Артефакты изменения (proposal, specs, design, tasks) остаются у выбранного инструмента. Параллельный spec или plan AI bro для того же изменения не заводи.

Ниже — тот же типовой путь «думаем → фиксируем → делаем → помним», но поверх [OpenSpec](https://github.com/Fission-AI/OpenSpec). Для Spec Kit и других spec-driven флоу логика та же: их команды оставляют артефакты, команды AI bro усиливают этапы.

### Кто за что отвечает

OpenSpec core: `/opsx:explore` → `/opsx:propose` → `/opsx:apply` → `/opsx:sync` → `/opsx:archive`. В Cursor команда может выглядеть как `/opsx-propose`.

| Этап | OpenSpec | AI bro |
|---|---|---|
| Идея сырая, нужно разобраться | `/opsx:explore` — размышление без файлов | `/bro-think-with-me` — прояснение, проверка идеи, дебаг, выбор подхода |
| Change: зачем, что меняется, как, чеклист | `/opsx:propose` — `proposal.md`, delta specs, `design.md`, `tasks.md` | `/bro-review-spec-plan` — независимое ревью этих файлов до кода |
| Реализация | `/opsx:apply` — идёт по `tasks.md` | `/bro-do-it` — реализация с коммитом, `/bro-review-code` и проверкой тестами |
| Сверка кода с постановкой | `/opsx:verify` (expanded-профиль) | `/bro-review-code` — уже внутри `/bro-do-it`, можно вызвать отдельно |
| Живые specs системы | `/opsx:sync` и `/opsx:archive` | не подменяй: delta specs вливает OpenSpec |
| Знания, которые не являются поведением системы | `openspec/specs/` — требования и сценарии | `/bro-remember-it` — контекст, конвенции, playbooks |

`/bro-give-me-spec` и `/bro-give-me-plan` в этом флоу **не** нужны: их роль уже закрывают proposal, specs и tasks OpenSpec. Их имеет смысл вызывать только если OpenSpec для этого изменения не используешь.

`openspec/specs/` и memory bank — разные слои. Specs описывают поведение системы. Банк — обзор, архитектура, нормы, типовые процедуры. Не копируй требования OpenSpec в `features/` как вторую спецификацию.

### Пример: rate limiting публичного API

В проекте уже есть OpenSpec. Нужно ограничить частоту запросов к публичному API.

**1. Думаем.** Идея ещё сырая — неясно, что именно ограничивать и зачем.

```text
/bro-think-with-me публичный API нужно ограничить по частоте запросов, не уверен с чего начать
```

Скилл остаётся в чтении: проясняет потребность, находит, как устроен текущий API, помогает выбрать рамки. `/opsx:explore` здесь можно не вызывать — это тот же этап «подумать до артефактов». Если хочешь остаться внутри команд OpenSpec, достаточно explore; оба сразу на один вопрос не запускай.

**2. Фиксируем change в OpenSpec.** Когда ясно, *что* должно получиться:

```text
/opsx:propose add-rate-limit
```

Появится `openspec/changes/add-rate-limit/` с proposal, delta specs, design и tasks. Это и есть постановка. Отдельный `memory-bank/changes/add-rate-limit/spec.md` не создавай.

**3. Ревьюим постановку, пока кода нет.**

```text
/bro-review-spec-plan проверь openspec/changes/add-rate-limit/proposal.md, specs/ и tasks.md
```

Если статус `NEEDS_WORK` — правь артефакты OpenSpec (`/opsx:update` или руками) и повтори ревью до `PASS`. Не чини замечания новым планом AI bro.

**4. Делаем.** Хозяин реализации — `/bro-do-it`: у него цикл коммит → ревью кода → тесты. `/opsx:apply` и `/opsx:verify` для этого change не вызывай.

```text
/bro-do-it выполни change add-rate-limit:
шаги из openspec/changes/add-rate-limit/tasks.md,
требования и сценарии из openspec/changes/add-rate-limit/specs/,
рамки из proposal.md и design.md
```

В постановке есть шаги — скилл идёт в режиме `plan` и не подменяет способ из `tasks.md` и `design.md`. После успеха сам вызовет `/bro-remember-it`.

Если предпочитаешь реализацию командой OpenSpec — `/opsx:apply`, а затем отдельно `/bro-review-code проверь текущую ветку относительно main`. Два реализатора на одно change не ставь.

**5. Вливаем specs.** Код готов, tasks закрыты:

```text
/opsx:archive
```

OpenSpec синхронизирует delta specs в `openspec/specs/` и убирает change в архив. Это его зона: AI bro сюда не вмешивается.

**6. Помним только устойчивое.** `/bro-do-it` уже вызвал `/bro-remember-it`. В банк попадёт то, что переживёт change: например, что лимитер сидит в middleware публичного API и какой playbook для новых эндпоинтов. Поведение «429 после N запросов» остаётся в `openspec/specs/` — второй раз его не записывай.

### Коротко

```text
/bro-think-with-me          → понять задачу
/opsx:propose               → артефакты изменения
/bro-review-spec-plan       → ревью постановки
/bro-do-it                  → реализация, ревью кода, тесты
/opsx:archive               → живые specs
/bro-remember-it            → знания проекта, не дубль specs
```

Тот же рисунок для другого инструмента: его команда «создать change/spec/plan» остаётся источником артефактов, AI bro подключается на думании, ревью и доведении до результата.

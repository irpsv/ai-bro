# File Spec

Workflow для спецификации как файлового артефакта.

## ОБЩИЕ ПРАВИЛА

- При составлении спецификации **ОБЯЗАТЕЛЬНО** соблюдай структуру разделов из [spec-template.md](../spec-template.md).
- После записи файла **ОБЯЗАТЕЛЬНО** проведи [ревью спецификации](../spec-review.md), если человек явно не попросил обойтись без ревью.

## ОГРАНИЧЕНИЯ / STOP

- **ЗАПРЕЩЕНО** выбирать путь размещения файла спецификации самому.
- **ЗАПРЕЩЕНО** записывать файл спецификации, пока человек не назвал однозначный путь. Путь, названный в текущем запросе, уже считается ответом — не спрашивай его повторно.
- Если файл по заданному пути уже существует — **ЗАПРЕЩЕНО** обновлять его без явного одобрения на обновление.
- **ЗАПРЕЩЕНО** пропускать ревью, кроме явной просьбы человека в текущем запуске.
- **ЗАПРЕЩЕНО** подменять публичный вызов `/bro-review-spec-plan` собственным ревью или своими субагентами-ревьюерами.
- **ЗАПРЕЩЕНО** предлагать `/bro-do-it` до `PASS` ревью или явного пропуска ревью.

## ПОРЯДОК РАБОТЫ

1. **ПРОЧИТАЙ** [spec-template.md](../spec-template.md).
2. **ОПРЕДЕЛИ** путь файла спецификации. Если человек уже назвал однозначный полный путь в запросе — используй его и **не спрашивай** повторно. Если пути нет или он двусмысленный — **СПРОСИ** полный путь. Путь **не** выбирай сам. Если файл по заданному пути уже есть — прочитай его, **СООБЩИ** человеку и получи явное одобрение на обновление.
3. **СОЗДАЙ** или **ОБНОВИ** файл спецификации по шаблону и заданному пути. Не жди отдельного апрува содержания перед записью.
4. Если человек явно не просил пропустить ревью — **ВЫПОЛНИ** цикл по [правилам ревью](../spec-review.md), обработай итоговый `PASS` / `NEEDS_WORK` / `BLOCKED`.
5. После завершения ревью (или после явного пропуска) **СООБЩИ** итог в чате. Отдельный апрув содержания не запрашивай: актуальный файл уже на диске.
6. Предложи `/bro-do-it` **только** при `PASS` ревью или при явном пропуске ревью по просьбе человека.

## Артефакты

### spec.md

Спецификация результата: самодостаточные границы, подтверждённые опоры, конечное состояние и критерии приемки — без шагов реализации.

`spec.md` **ДОЛЖЕН** содержать разделы:
- `Задача и контекст`
- `Целевой результат`
- `Принятые решения`
- `Рамки задачи`
- `Критерии приемки`

Раздел `Принятые решения` **МОЖЕТ** присутствовать только если есть зафиксированные договорённости. Иначе раздел **НЕ** создавай.

## Quality Control

Перед завершением проверь:

- артефакт находится по заданному человеком пути;
- путь назвал человек (в запросе или в ответ на вопрос) до первой записи; если файл уже существовал — получено одобрение на обновление;
- в артефакте есть разделы шаблона и нет лишних;
- нет шагов, этапов и способа реализации; существующие пути — только якорь текущего состояния;
- каждый изменяемый сценарий покрыт критерием приемки;
- каждый критерий наблюдаем без описания способа проверки;
- ревью выполнено через `/bro-review-spec-plan` (или явно пропущено человеком);- при `NEEDS_WORK` файл обновлён, при `BLOCKED` задан вопрос человеку;
- `/bro-do-it` предложен только после `PASS` или явного пропуска ревью.

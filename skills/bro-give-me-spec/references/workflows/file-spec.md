# File Spec

Workflow для спецификации как файлового артефакта. Сюда же относится `delta-<N>-<slug>.md` рядом с реализованным `spec.md`.

## ОБЩИЕ ПРАВИЛА

- При составлении спецификации **ОБЯЗАТЕЛЬНО** соблюдай структуру разделов из [spec-template.md](../spec-template.md). Разделы «Правила frontmatter» и «Правила файла дельты» в шаблоне — канон оформления, **не** включай их в тело записываемого файла.
- В начале каждого нового `spec.md` и каждого `delta-<N>-<slug>.md` — только frontmatter из шаблона: `readonly: false`, `is_implemented: false`.
- После записи файла **ОБЯЗАТЕЛЬНО** проведи [ревью спецификации](../spec-review.md), если человек явно не попросил обойтись без ревью.

## ОГРАНИЧЕНИЯ / STOP

- **ЗАПРЕЩЕНО** выбирать путь размещения `spec.md` самому.
- **ЗАПРЕЩЕНО** записывать `spec.md`, пока человек не назвал однозначный путь. Путь, названный в текущем запросе, уже считается ответом — не спрашивай его повторно.
- Если `spec.md` по заданному пути уже существует — **ЗАПРЕЩЕНО** обновлять его без явного одобрения на обновление.
- **ЗАПРЕЩЕНО** менять любой файл спецификации (`spec.md` или `delta-<N>-<slug>.md`), если в его frontmatter `is_implemented: true` или `readonly: true`.
- **ЗАПРЕЩЕНО** обновлять реализованный `spec.md` на месте. Для изменения результата после реализации создай новый `delta-<N>-<slug>.md` в том же каталоге `changes/<feature-id>/`.
- Имя `delta-<N>-<slug>.md` собирай сам: `N` — наименьшее свободное среди `delta-<N>-*.md` в каталоге; `slug` — kebab-case из краткого смысла дельты. Имя delta-файла у человека **не** спрашивай.
- Если каталог реализованной спеки неизвестен — **СПРОСИ** путь к `spec.md` или к каталогу `changes/<feature-id>/`. Имя delta-файла при этом **не** спрашивай.
- **ЗАПРЕЩЕНО** пропускать ревью, кроме явной просьбы человека в текущем запуске.
- **ЗАПРЕЩЕНО** подменять вызов `/bro-review-spec-plan` собственной проверкой или своими субагентами-ревьюерами.
- **ЗАПРЕЩЕНО** после `NEEDS_WORK` снова вызывать `/bro-review-spec-plan`.
- **ЗАПРЕЩЕНО** предлагать `/bro-do-it` до `PASS` ревью или явного пропуска ревью.
- **ЗАПРЕЩЕНО** после `PASS` ревью или явного пропуска предлагать следующий шаг кроме `/bro-do-it`.
- **ЗАПРЕЩЕНО** предлагать план реализации или `/bro-give-me-plan`.

## ПОРЯДОК РАБОТЫ

1. **ПРОЧИТАЙ** [spec-template.md](../spec-template.md).
2. **ОПРЕДЕЛИ** целевой артефакт:
   - новая спека без реализованного `spec.md` — человек задаёт путь к `spec.md`; путь **не** выбирай сам;
   - нереализованный `spec.md` по известному пути — прочитай файл; если путь уже был в запросе — используй его; если файл есть — **СООБЩИ** человеку и получи явное одобрение на обновление;
   - реализованный `spec.md` (`is_implemented: true`) — **не** обновляй; создай `delta-<N>-<slug>.md` в том же каталоге по правилам дельты в [spec-template.md](../spec-template.md);
   - нереализованный `delta-<N>-<slug>.md` по пути от человека — как для нереализованного `spec.md`: одобрение на обновление, если файл уже есть.
3. **СОЗДАЙ** или **ОБНОВИ** файл по шаблону. Для дельты включи ссылку на `spec.md` того же каталога и только изменившиеся разделы. Не жди отдельного апрува содержания перед записью.
4. Если человек явно не просил пропустить ревью — **ВЫПОЛНИ** цикл по [правилам ревью](../spec-review.md) для записанного файла (`spec.md` или delta).
5. После завершения ревью (или после явного пропуска) **СООБЩИ** итог в чате. Отдельный апрув содержания не запрашивай: актуальный файл уже на диске.
6. Если ревью завершилось `PASS` или человек явно пропустил ревью — **ПОДСКАЖИ** единственный следующий шаг: `/bro-do-it`. Иначе следующий шаг не предлагай.

## Артефакты

### spec.md

Спецификация результата: самодостаточные границы, подтверждённые опоры, конечное состояние и критерии приемки — без шагов реализации.

`spec.md` **ДОЛЖЕН** содержать разделы:
- `Задача и контекст`
- `Целевой результат`
- `Принятые решения`
- `Рамки задачи`
- `Критерии приемки`

Раздел `Принятые решения` **МОЖЕТ** присутствовать только если есть зафиксированные договорённости. Иначе раздел **НЕ** создавай.

### delta-<N>-<slug>.md

Дельта результата поверх реализованного `spec.md` в том же каталоге. Frontmatter — как у спецификации. Обязательна ссылка на `spec.md` каталога. Только изменившиеся разделы шаблона; критерии приёмки — только на дельту.

## Quality Control

Перед завершением проверь:

- артефакт находится по согласованному пути (`spec.md` от человека или `delta-*`, имя которого выбрал агент);
- для `spec.md` путь назвал человек до первой записи; если файл уже существовал — получено одобрение на обновление;
- реализованный `spec.md` не перезаписан; при необходимости создан delta рядом;
- frontmatter нового файла — только `readonly: false` и `is_implemented: false`;
- в артефакте есть нужные разделы шаблона и нет лишних; у дельты есть ссылка на `spec.md`;
- нет шагов: нет порядка действий;
- каждый изменяемый сценарий покрыт критерием приемки;
- каждый критерий наблюдаем без описания способа проверки;
- независимое ревью доведено до `PASS` или `NEEDS_WORK` через `/bro-review-spec-plan` (или явно пропущено человеком);
- после `NEEDS_WORK` повторного `/bro-review-spec-plan` не было, замечания из этого списка закрыты;
- при `BLOCKED` задан вопрос человеку;
- после `PASS` или явного пропуска ревью предложен единственный следующий шаг `/bro-do-it`; план реализации не предложен;
- `/bro-do-it` не предложен до `PASS` или явного пропуска и не предложен при остановке без `PASS`.

# Delta Spec

Workflow для правок спецификации.

## ПРАВИЛА WORKFLOW

- При составлении спецификации **ОБЯЗАТЕЛЬНО** соблюдай структуру разделов из [spec-template.md](../spec-template.md). Разделы «Правила frontmatter» и «Правила файла дельты» в шаблоне — канон оформления, **не** включай их в тело записываемого файла.
- Пока `spec.md` не реализован, правка идёт в него. Имя и состав нового файла дельты — по разделу «Правила файла дельты» в [spec-template.md](../spec-template.md).
- После записи файла **ОБЯЗАТЕЛЬНО** проведи [ревью спецификации](../spec-review.md), если человек явно не попросил обойтись без ревью.
- **ЗАПРЕЩЕНО** обновлять и менять файл спецификации, если в его frontmatter `is_implemented: true` или `readonly: true`.
- Если каталог реализованной спеки неизвестен — **СПРОСИ** путь к `spec.md` или к каталогу `changes/<feature-id>/`. **МОЖНО** сформировать имя delta-файла самостоятельно.
- **ЗАПРЕЩЕНО** пропускать ревью, кроме явной просьбы человека в текущем запуске.
- **ЗАПРЕЩЕНО** подменять вызов `/bro-review-spec-plan` собственной проверкой или своими субагентами-ревьюерами.
- **ЗАПРЕЩЕНО** после `NEEDS_WORK` снова вызывать `/bro-review-spec-plan`.
- **ЗАПРЕЩЕНО** предлагать `/bro-do-it` до `PASS` ревью или явного пропуска ревью.
- **ЗАПРЕЩЕНО** после `PASS` ревью или явного пропуска предлагать следующий шаг кроме `/bro-do-it`.
- **ЗАПРЕЩЕНО** предлагать составить план реализации или `/bro-give-me-plan`.

## ПОРЯДОК РАБОТЫ

1. **ПРОЧИТАЙ** [spec-template.md](../spec-template.md).
2. **ПРОЧИТАЙ** frontmatter существующего файла.
3. **ОПРЕДЕЛИ** целевой артефакт:
   - нереализованный `spec.md` (`is_implemented: false`) по известному пути — прочитай файл; если путь уже был в запросе — используй его; если файл есть — **СООБЩИ** человеку и получи явное одобрение на обновление;
   - реализованный `spec.md` (`is_implemented: true`) — **не** обновляй; создай `delta-<N>-<slug>.md` в том же каталоге по правилам дельты в [spec-template.md](../spec-template.md);
   - нереализованный `delta-<N>-<slug>.md` (`is_implemented: false`) по пути от человека — как для нереализованного `spec.md`: одобрение на обновление, если файл уже есть.
4. **СОЗДАЙ** или **ОБНОВИ** файл по шаблону. Для дельты включи ссылку на `spec.md` того же каталога и только изменившиеся разделы. Не жди отдельного апрува содержания перед записью.
5. Если человек явно не просил пропустить ревью — **ВЫПОЛНИ** цикл по [правилам ревью](../spec-review.md) для записанного файла.
6. После завершения ревью (или после явного пропуска) **СООБЩИ** итог в чате. Отдельный апрув содержания не запрашивай: актуальный файл уже на диске.
7. Если ревью завершилось `PASS` или человек явно пропустил ревью — **ПОДСКАЖИ** единственный следующий шаг: `/bro-do-it`. Иначе следующий шаг не предлагай.

## Артефакты

### delta-<N>-<slug>.md

Дельта результата поверх реализованного `spec.md` в том же каталоге. Frontmatter — как у спецификации. Обязательна ссылка на `spec.md` каталога. Только изменившиеся разделы шаблона; критерии приёмки — только на дельту.

## Quality Control

Перед завершением проверь:

- если файл уже существовал — получено одобрение на обновление;
- frontmatter нового файла — только `readonly: false` и `is_implemented: false`;
- в артефакте есть нужные разделы шаблона и нет лишних; у дельты есть ссылка на `spec.md`;
- каждый изменяемый сценарий покрыт критерием приемки;
- каждый критерий наблюдаем без описания способа проверки;
- независимое ревью доведено до `PASS` или `NEEDS_WORK` через `/bro-review-spec-plan` (или явно пропущено человеком);
- после `NEEDS_WORK` повторного `/bro-review-spec-plan` не было, замечания из этого списка закрыты;
- при `BLOCKED` задан вопрос человеку;
- после `PASS` или явного пропуска ревью предложен единственный следующий шаг `/bro-do-it`; план реализации не предложен;
- `/bro-do-it` не предложен до `PASS` или явного пропуска и не предложен при остановке без `PASS`.

# review-comments

## Главная задача

Разобрать чужие замечания к уже сделанным изменениям. По каждому решить, справедливо ли оно, и зафиксировать, что с ним делать.

Этот workflow отвечает на вопрос «что делаем с замечаниями ревью?». Контекст ситуации — сами замечания: текст в сообщении или ссылка на PR/MR. Итог — текст со списком решений, по одному блоку на замечание. Код, план и артефакты этот workflow не создаёт.

Он не ищет неизвестную причину сбоя — для этого `debug`. Он не выбирает подход к новому поведению — для этого `design-solution`. Он не проводит ревью diff и не составляет свои замечания.

## Как вести разговор

1. Собери замечания из сообщения. Если есть ссылка на PR или MR, а текста замечаний нет, прочитай их сам.
2. Если замечаний нет и ссылки, по которой их можно прочитать, тоже нет, остановись и задай вопрос: где замечания. Без этого списка разбор не начать.
3. Иди по каждому замечанию отдельно. Не склеивай разные претензии в один блок.
4. Для вердикта сверь претензию с кодом и с постоянными знаниями проекта, если они есть. Если из контекста вердикт не следует, собери выжимку через explorer.
5. По каждому замечанию сразу отдай блок в формате раздела «Допустимый итог». Не откладывай его до закрытия списка.
6. Вопрос задавай только по правилам выбора вопросов. Иначе назови допущение и ставь вердикт. Не спрашивай подтверждение вердикта и не спрашивай, с какого замечания начать.
7. Замечание закрыто, когда человек принял вердикт или поправил его. Пока спор по замечанию открыт, не подменяй его соседней задачей.

## Когда переключаться

- По замечанию причина сбоя неизвестна, и человек хочет установить именно её, а не решить судьбу списка — переключись на `debug`.
- Замечание требует выбрать новое поведение, и это стало отдельной задачей вместо разбора списка — переключись на `design-solution`.
- Неясно, какую претензию вообще обсуждаем — переключись на `explore`.

Пока главная задача — решить, что делать со списком замечаний, оставайся в этом workflow. Похожесть одного пункта на баг или на спор о поведении сама по себе повод для переключения не даёт: поставь по нему блок с вердиктом «неясно».

## Когда завершать

- По каждому замечанию есть заполненный блок в формате раздела «Допустимый итог».
- Открытых споров по списку нет: человек принял вердикты или поправил их.
- Для следующего шага нужен уже не разбор замечаний, а реализация согласованного списка.

## Допустимый итог

Каждый ответ по замечанию и закрывающий список состоят из блоков ниже. Один блок — одно замечание:
```markdown
**Замечание:** суть своими словами.
**Вердикт:** берём, не берём или неясно.
**Почему:** на чём держится вердикт. Для «не берём» здесь же напиши, почему претензия не держится.
```

Для «берём» добавь в тот же блок:
```markdown
**Что меняем:** какое изменение закрывает замечание.
**Как понять, что готово:** наблюдаемый признак, по которому видно, что изменение сделано.
```

Для «неясно» добавь в тот же блок:
```markdown
**Какого факта не хватает:** что нужно узнать, чтобы выбрать «берём» или «не берём».
```

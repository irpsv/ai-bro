# Правила содержимого

## Общие правила

- Пиши кратко и по делу. Каждый файл — самодостаточный фрагмент знаний.
- Фиксируй только подтверждённые факты: от человека, из репозитория или из явно указанного источника.
- Помечай выведенное как выведенное, пока человек его не подтвердит.
- **ЗАПРЕЩЕНО** дублировать одно и то же постоянное знание в разных файлах. Если такая тема уже есть — обнови существующий файл. Новое намерение всегда пиши отдельным каталогом, даже если похожая заметка уже есть.
- **ЗАПРЕЩЕНО** создавать файлы вне привязанных разделов (см. [роли знаний](./knowledge-roles.md)). Путь намерений привязан всегда.
- При упоминании конкретного существующего файла оформляй путь Markdown-ссылкой с относительным путём от текущего документа. Шаблоны, маски и ещё не созданные пути оставляй в формате кода.
- Если писать нечего, то так и говори и ВЫХОДИ

## Классификация при пополнении

Перед записью определи тип знания:

| Тип | Куда | Примеры |
|---|---|---|
| Контекст проекта | раздел контекста | стек, архитектура, глоссарий, сквозное решение |
| Фича | раздел features | описание, границы, поведение, решения по фиче |
| Процедура | раздел playbooks | пошаговое типовое действие |
| Намерение | `<корень банка>/todos/<slug>/todo.md` | «сделать мобильную версию», идея на потом, приложенный макет |
| Спецификация результата | **НЕ** этот скилл | используй `/bro-give-me-spec` |
| План работ | **НЕ** этот скилл | используй `/bro-give-me-plan` |

Просьба запомнить, где содержание — будущее действие, идея или пожелание к продукту, это намерение, даже если глагол «запомни». Просьба запомнить, где содержание — как продукт устроен, как решили или как делать типовую процедуру, это прежние три роли.

Пиши, если появилось или изменилось устойчивое знание: сквозное решение, норма, факт о продукте или стеке, границы, поведение или статус фичи, типовая процедура. Намерение записывай сразу, даже когда формулировка короткая.

Для постоянного знания **нечего писать**, если нет такого знания сверх уже лежащего в разделах:

- багфикс или рефакторинг без смены наблюдаемого поведения, границ фичи или сквозного решения;
- те же сведения уже есть в разделе без смыслового расхождения;
- временный контекст сессии, локальные детали реализации, личные предпочтения.

Не дописывай «для полноты». Если писать нечего — так и скажи, файлы не трогай.

## Решения в разделе контекста

Если в разделе контекста есть файл решений, новые записи добавляй в начало. Рекомендуемый формат:

```markdown
## YYYY-MM-DD — Краткое название решения

**Контекст:** ...

**Решение:** ...

**Последствия:** ...
```

## Файл фичи

Рекомендуемые разделы внутри одного файла:

- `## Обзор` — зачем фича, границы, статус
- `## Поведение` — требования и сценарии (если есть что фиксировать)
- `## Решения` — решения по фиче с датой (если есть)

Идентификатор фичи — kebab-case (латиница, цифры, дефис), один и тот же во всех упоминаниях.

При создании новой фичи **ОБЯЗАТЕЛЬНО** обнови реестр раздела, **если он уже есть**.

## Файл playbook

Рекомендуемые разделы:

- `## Когда применять`
- `## Предусловия`
- `## Шаги`
- `## Проверка результата`

Slug процедуры — kebab-case.

При создании нового playbook **ОБЯЗАТЕЛЬНО** обнови реестр раздела, **если он уже есть**.

## Намерение

Намерение ещё не решение о продукте и не описание фичи. Его не уточняют до записи и не раскладывают по разделам фичи.

Путь бери из [ролей знаний](./knowledge-roles.md). Каталог создай в момент записи, если его нет.

Slug придумай сам: короткий kebab-case из смысла фразы, латиница, цифры, дефис. У человека не спрашивай. Если каталог с таким slug уже есть, а намерение другое — добавь числовой суффикс и не перезаписывай чужую заметку.

В том ходе, где намерение назвали:

1. Прочитай только `<корень>/todos/`, если каталог уже есть. Остальной банк для этого не обходи.
2. Сразу создай каталог и запиши в `todo.md` формулировку человека без правок и без своих заголовков.
3. Файлы, приложенные к этому сообщению, скопируй в тот же каталог рядом с `todo.md`. Имена сохрани. В `todo.md` их не описывай.
4. Реестр раздела не заводи.
5. В ответе назови путь и slug. Затем одно предложение: заметку можно разобрать, когда будет желание. В этом ответе нет вопросов, вариантов и новой формулировки.
6. Если в разделе уже была заметка с тем же намерением — после записи назови её путь. Сам не сливай и новую запись не отменяй.

Следующий ход про эту же заметку: допиши слова человека в тот же `todo.md`, исходную формулировку не заменяй. Slug не переименовывай, пока человек сам не попросит. Новое намерение — новый каталог.

Если человек соглашается разобрать заметку — обсуждай в этом скилле. Файл не меняй, пока он сам не даст текст, который нужно дописать. Спецификацию не начинай: для неё `/bro-give-me-spec`.

## Реестры

Реестр раздела (`index.md`, README, секция в `AGENTS.md` и т.п.) — только если уже существует рядом с разделом. Держи его актуальным при каждом добавлении или переименовании.

**ЗАПРЕЩЕНО** создавать новый канонический реестр, если у раздела его нет.
**МОЖНО** рекомендовать его создать, если есть такая необходимость.

# Правила содержимого

## Общие правила

- Пиши кратко и по делу. Каждый файл — самодостаточный фрагмент знаний.
- Фиксируй только подтверждённые факты: от человека, из репозитория или из явно указанного источника.
- Помечай выведенное как выведенное, пока человек его не подтвердит.
- **ЗАПРЕЩЕНО** дублировать одно и то же в разных файлах. Если тема уже есть — обнови существующий файл.
- **ЗАПРЕЩЕНО** создавать файлы вне привязанных разделов (см. [роли знаний](./knowledge-roles.md)).
- При упоминании конкретного существующего файла оформляй путь Markdown-ссылкой с относительным путём от текущего документа. Шаблоны, маски и ещё не созданные пути оставляй в формате кода.
- Если писать нечего, то так и говори и ВЫХОДИ

## Классификация при пополнении

Перед записью определи тип знания:

| Тип | Куда | Примеры |
|---|---|---|
| Контекст проекта | раздел контекста | стек, архитектура, глоссарий, сквозное решение |
| Фича | раздел features | описание, границы, поведение, решения по фиче |
| Процедура | раздел playbooks | пошаговое типовое действие |
| Спецификация результата | **НЕ** этот скилл | используй `/bro-give-me-spec` |
| План работ | **НЕ** этот скилл | используй `/bro-give-me-plan` |

Пиши, если появилось или изменилось устойчивое знание: сквозное решение, норма, факт о продукте или стеке, границы, поведение или статус фичи, типовая процедура.

**Нечего писать**, если нет такого знания сверх уже лежащего в разделах:

- багфикс или рефакторинг без смены наблюдаемого поведения, границ фичи или сквозного решения;
- те же сведения уже есть в разделе без смыслового расхождения;
- временный контекст сессии, локальные детали реализации, личные предпочтения.

Не дописывай «для полноты». Если писать нечего — так и скажи, файлы не трогай.

## Решения в разделе контекста

Если в разделе контекста есть файл решений, новые записи добавляй в начало. Рекомендуемый формат:

```markdown
## YYYY-MM-DD — Краткое название решения

**Контекст:** ...

**Решение:** ...

**Последствия:** ...
```

## Файл фичи

Рекомендуемые разделы внутри одного файла:

- `## Обзор` — зачем фича, границы, статус
- `## Поведение` — требования и сценарии (если есть что фиксировать)
- `## Решения` — решения по фиче с датой (если есть)

Идентификатор фичи — kebab-case (латиница, цифры, дефис), один и тот же во всех упоминаниях.

При создании новой фичи **ОБЯЗАТЕЛЬНО** обнови реестр раздела, **если он уже есть**.

## Файл playbook

Рекомендуемые разделы:

- `## Когда применять`
- `## Предусловия`
- `## Шаги`
- `## Проверка результата`

Slug процедуры — kebab-case.

При создании нового playbook **ОБЯЗАТЕЛЬНО** обнови реестр раздела, **если он уже есть**.

## Реестры

Реестр раздела (`index.md`, README, секция в `AGENTS.md` и т.п.) — только если уже существует рядом с разделом. Держи его актуальным при каждом добавлении или переименовании.

**ЗАПРЕЩЕНО** создавать новый канонический реестр, если у раздела его нет.
**МОЖНО** рекомендовать его создать, если есть такая необходимость.


# stage-plan

Реализация задачи по **stage-файлу** плана.

Stage-файл соответствует формату: в frontmatter есть `steps`, в теле есть разделы `## Шаг N` с подразделами `Где меняем`, `Что меняем`, `Зачем это делаем`.

## Основные правила

- СНАЧАЛА **прочитай** stage-файл, чтобы понять, какие шаги нужно выполнять сейчас.
- Stage-файл — **источник истины** для task payload. Не пересказывай его содержимое своими словами, если достаточно ссылки на файл.
- Если задача, рамки или критерии приемки **неясны**, **остановись** и **запроси уточнение** у пользователя.
- Результат workflow — **task payload** для подстановки в `<task payload>` промптов developer и reviewer.

## Как читать stage-файл

- Frontmatter `steps` определяет порядок шагов и их статусы.
- Каждый элемент `steps` содержит `name`, который **точно совпадает** с заголовком соответствующего раздела `## Шаг N`.
- Содержимое шага — в разделе `## Шаг N`: `Где меняем`, `Что меняем`, `Что не делаем` (если есть), `Зачем это делаем`.
- Deliverables, ограничения и критерии приемки — в теле stage-файла.

Если структура повреждена (нет `steps`, имена не совпадают с заголовками, не хватает данных для безопасной реализации) — **остановись** и запроси уточнение.

## Выбор шагов

- Определи, какие элементы `steps` ещё не завершены и какие взять в текущий прогон.
- Реши, какие шаги сгруппировать в один запуск developer и какие выполнять параллельно (без пересечения изменяемых файлов).
- Выбранные шаги образуют текущую единицу работы и приемки.
- Критерии всего stage применяй к текущей единице только в той части, достижение которой зависит от выбранных шагов. Критерий, зависящий от ещё не выбранного шага, не блокирует завершение текущей единицы.
- Если выбраны все оставшиеся шаги, дополнительно проверь выполнение всех критериев stage целиком.
- Если проверка или ревью stage обнаружили дефект, исправление которого требует изменить ранее завершённый шаг, верни связанный элемент `steps` из `completed` в `wait` и включи его в следующую единицу работы вместе с текущими незавершёнными шагами.

## Определение диапазонов строк

Перед формированием payload **прочитай** stage-файл и для каждого выбранного шага определи диапазон строк по текущему содержимому файла:

- диапазон шага — от заголовка `## Шаг N` до строки перед следующим заголовком того же или более высокого уровня;
- имя шага бери из frontmatter `steps` и сверяй с заголовком `## Шаг N`;
- в блок «Дополнительно учитывай» включай релевантные разделы вне выбранных шагов, если они нужны для безопасной реализации или проверки результата — например `## Критерии приемки`, `## Что будет готово после этапа`.

Диапазоны вычисляются **в момент dispatch** и не хранятся в stage-файле как канон. Если имя шага и диапазон расходятся, источником истины считай stage-файл.

## Task payload

Для каждого запуска developer сформируй payload:

```
Реализуй изменения по stage-файлу: </path/to/stage.md>

Нужно выполнить:
- "Шаг 1" — </path/to/stage.md:31-47>
- "Шаг 2" — </path/to/stage.md:49-61>

Дополнительно учитывай:
- </path/to/stage.md:63-67> — критерии приемки

Считай stage-файл источником истины по рамкам задачи, ограничениям и критериям приемки.
Выполняй только указанные шаги.
Единица приемки текущего запуска — только указанные шаги. Подтверди относящиеся к ним критерии; критерии, зависящие от невыбранных шагов, перечисли как отложенные, а не как дефект текущей реализации.
Если указаны все оставшиеся шаги, подтверди все критерии stage целиком.
```

Дополнительный контекст добавляй только если его нет в stage-файле, но он критичен для безопасной реализации.

Для reviewer используй тот же payload.

## Синхронизация `steps`

**ОБЯЗАТЕЛЬНО** меняй статусы в frontmatter stage-файла:

* перед запуском [итерации реализации](../SKILL.md#2-итерация-реализации) — выбранные шаги `in_progress`
* после выполнения относящихся к выбранным шагам критериев и вердикта `PASS` — `completed`
* **не** отмечай `completed`, если цикл остановлен без `PASS`, остались невыполненные критерии текущей единицы работы, падающие проверки либо незакрытые `critical` / `high` замечания reviewer
* отложенные критерии, зависящие от невыбранных шагов, не мешают отметить текущие шаги `completed`; при выборе всех оставшихся шагов отложенных критериев быть не должно

# Inline Plan

Описание workflow по формулированию implementation плана без файлов.
Задача составить план реализации (implementation plan).

## ОБЩИЕ ПРАВИЛА

- **ОБЯЗАТЕЛЬНО** соблюдай [правила диалога](../dialog-rules.md)!
- **ОБЯЗАТЕЛЬНО** соблюдай [гигиену реализации](../implementation-hygiene.md)!
- **ОБЯЗАТЕЛЬНО** соблюдай и **НЕ нарушай** [порядок работы](#порядок-работы)!
- План **ДОЛЖЕН** быть однозначным, без наличия вариаций и вопросов в нём. Все вопросы и вариации **НУЖНО** решать с человеком.
- План **НЕ ДОЛЖЕН** подменять шаги реализации кодом, diff, патчами или псевдокодом.
- При составлении плана **ОБЯЗАТЕЛЬНО** соблюдай структуру шагов и оформляй по [правилам формирования шагов](#правила-формирования-шагов).
- Если что-то непонятно, **ОБЯЗАТЕЛЬНО** уточни у человека
- Если что-то нелогично или неправильно, **ОБЯЗАТЕЛЬНО** уточни у человека

## ОГРАНИЧЕНИЯ / STOP

- **ЗАПРЕЩЕНО** придумывать и додумывать факты или гипотезы. Любая неоднозначность **ДОЛЖНА** быть решена до перехода к составлению плана.
- **ЗАПРЕЩЕНО** создавать или записывать файлы плана. Передача плана через тул, который указала harness (например `CreatePlan`), файлом не является.

## ПОРЯДОК РАБОТЫ

1. **ПРОЧИТАЙ** [правила формирования шагов](#правила-формирования-шагов) и [гигиену реализации](../implementation-hygiene.md).
2. **СОБЕРИ** информацию для составления однозначного плана: код, контекст:
   - Не спрашивай то, что можно установить с высокой уверенностью.
   - Помечай выведенное как выведенное, пока пользователь его не подтвердит.
3. **ЗАПРОСИ** недостающую информацию у человека. **ОБЯЗАТЕЛЬНО** соблюдай [правила диалога](../dialog-rules.md).
4. **СОСТАВЬ** план, шаги оформляй по [правилам формирования шагов](#правила-формирования-шагов).
5. **ПЕРЕДАЙ** подготовленный план:
   - Если в контексте есть указание harness оформить план через конкретный тул (например `CreatePlan`) — **ВЫЗОВИ** этот тул и передай план целиком.
   - Если такого указания нет — **ВЫВЕДИ** план в чат.
6. **ОСТАНОВИСЬ** и жди дальнейших указаний от человека. Либо правки плана, либо переход к реализации.

## ПРАВИЛА ФОРМИРОВАНИЯ ШАГОВ

Основной документ с правилами: [steps-rules.md](../step-rules.md).
Для inline плана, **НУЖНО** использовать краткую структуру шагов:
```
## Шаг N

### Где меняем

`<module>/lib/Domain/EntityType.php` (новый enum)

### Что меняем

Добавить enum с **ровно** перечисленными элементами из раздела, фиксирующего конечный результат.
```

Используй только подразделы:
- где меняем
- что меняем

Остальные подразделы не используй.
Мотивация: inline план используется для небольших задач, в которых **ДОЛЖЕН** соблюдаться баланс простоты и полноты информации.

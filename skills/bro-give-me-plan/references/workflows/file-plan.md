# File Plan

Описание workflow по созданию implementation плана как файлового артефакта.
Задача составить план реализации (implementation plan).

## ОБЩИЕ ПРАВИЛА

- **ОБЯЗАТЕЛЬНО** соблюдай [правила диалога](../dialog-rules.md)!
- **ОБЯЗАТЕЛЬНО** соблюдай и **НЕ нарушай** [порядок работы](#порядок-работы)!
- План **ДОЛЖЕН** быть однозначным, без наличия вариаций и вопросов в нём. Все вопросы и вариации **НУЖНО** решать с человеком.
- План **НЕ ДОЛЖЕН** подменять шаги реализации кодом, diff, патчами или псевдокодом.
- Если для описания шага требуется фрагмент реализации, шаг **НУЖНО** переписать на более высокий уровень абстракции.
- При составлении плана **ОБЯЗАТЕЛЬНО** соблюдай структуру разделов из [file-plan-template.md](../templates/file-plan-template.md).
- Разделы со шагами **ОБЯЗАТЕЛЬНО** оформляй по [step-rules.md](../step-rules.md).
- Если что-то непонятно, **ОБЯЗАТЕЛЬНО** уточни у человека
- Если что-то нелогично или неправильно, **ОБЯЗАТЕЛЬНО** уточни у человека
- После записи файла **ОБЯЗАТЕЛЬНО** проведи [ревью плана](../plan-review.md), если человек явно не попросил обойтись без ревью.

## ОГРАНИЧЕНИЯ / STOP

- **ЗАПРЕЩЕНО** придумывать и додумывать факты или гипотезы. Любая неоднозначность **ДОЛЖНА** быть решена до перехода к составлению плана.
- **ЗАПРЕЩЕНО** выбирать путь размещения файла плана самому.
- **ЗАПРЕЩЕНО** записывать файл плана, пока человек не назвал однозначный путь. Путь, названный в текущем запросе, уже считается ответом — не спрашивай его повторно.
- Если файл по заданному пути уже существует — **ЗАПРЕЩЕНО** обновлять его без явного одобрения на обновление.
- **ЗАПРЕЩЕНО** пропускать ревью, кроме явной просьбы человека в текущем запуске.
- **ЗАПРЕЩЕНО** подменять публичный вызов `/bro-review-spec-plan` собственным ревью или своими субагентами-ревьюерами.
- **ЗАПРЕЩЕНО** предлагать `/bro-do-it` до `PASS` ревью или явного пропуска ревью.

## ПОРЯДОК РАБОТЫ

1. **ПРОЧИТАЙ** [file-plan-template.md](../templates/file-plan-template.md) и [step-rules.md](../step-rules.md).
2. **СОБЕРИ** информацию для составления однозначного плана: код, контекст:
   - Не спрашивай то, что можно установить с высокой уверенностью.
   - Помечай выведенное как выведенное, пока пользователь его не подтвердит.
3. **ЗАПРОСИ** недостающую информацию у человека. **ОБЯЗАТЕЛЬНО** соблюдай [правила диалога](../dialog-rules.md).
4. **ОПРЕДЕЛИ** путь файла плана. Если человек уже назвал однозначный полный путь в запросе — используй его и **не спрашивай** повторно. Если пути нет или он двусмысленный — **СПРОСИ** полный путь. Путь **не** выбирай сам. Если файл по заданному пути уже есть — **СООБЩИ** и получи явное одобрение на обновление.
5. **ОСТАНОВИСЬ** и дождись одобрения человека, либо его корректировок.
6. **СОЗДАЙ** файл [артефакт плана](#planmd) по заданному пути.
7. Если человек явно не просил пропустить ревью — **ВЫПОЛНИ** цикл по [правилам ревью](../plan-review.md), обработай итоговый `PASS` / `NEEDS_WORK` / `BLOCKED`.
8. После завершения ревью (или после явного пропуска) **СООБЩИ** итог в чате. Отдельный апрув содержания не запрашивай: актуальный файл уже на диске.
9. Предложи `/bro-do-it` **только** при `PASS` ревью или при явном пропуске ревью по просьбе человека.

## Артефакты

### plan.md

Implementation план задачи: самодостаточные границы, подтверждённые опоры, конечное состояние, критерии приемки и шаги.

`plan.md` **ДОЛЖЕН** содержать разделы:
- `Задача и контекст`
- `Целевой результат`
- `Принятые решения`
- `Рамки задачи`
- `Критерии приемки`
- `Шаг 1..N`

Раздел `Принятые решения` **МОЖЕТ** присутствовать только если есть зафиксированные договорённости. Иначе раздел **НЕ** создавай.

## Quality Control

Перед завершением проверь:

- артефакт находится по заданному человеком пути;
- путь назвал человек (в запросе или в ответ на вопрос) до первой записи; если файл уже существовал — получено одобрение на обновление;
- в артефакте есть разделы шаблона и нет лишних;
- нет кода, diff, патчей и псевдокода;
- шаги оформлены по правилам шагов; при тестовых шагах есть шаг остановки;
- каждый изменяемый сценарий покрыт критерием приемки;
- каждый критерий наблюдаем без описания способа проверки;
- ревью выполнено через `/bro-review-spec-plan` (или явно пропущено человеком);
- при `NEEDS_WORK` файл обновлён, при `BLOCKED` задан вопрос человеку;
- `/bro-do-it` предложен только после `PASS` или явного пропуска ревью.
